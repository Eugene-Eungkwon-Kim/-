## ⚠️ 특별 검토 영역

### 2.1 데이터 소스 검증

**문제**: LG 외장하드 D:\ 드라이브 가용성
```
질문:
  • building_registry.db, transaction.db가 실제로 존재하는가?
  • 파일 포맷과 스키마가 명세서와 일치하는가?
  • 1,085개 마스터 리스트와의 매칭률 예상이 합리적인가? (85%)

리스크:
  • DB 접근 불가 → API Fallback으로 모두 해결 가능? (예상 90%)
  • 매칭률이 85% 미만일 경우 → 일정 지연 가능성?

권고:
  • 사전 데이터 마이그레이션 권장 (D:\ → 클라우드 스토리지)
  • 매칭률 85% 미달 시 대응 계획 필요
```

### 2.2 API 통합 검증

**문제**: Data.go.kr API 신뢰성
```
질문:
  • API 키 발급 현황? (문서: "발급받음")
  • Rate Limit (0.5초/요청) 준수 시 총 소요 시간? (계산: 2,170건 × 0.5초 = ~30시간)
  • 따라서 실제 가용 시간 24시간 이내로 완료 가능한가?

계산:
  Phase 3.1 (공시가격): 2,170건 × 0.5초 = ~30시간 ← 대기 포함하면 11시간 실행 가능
  Phase 3.2 (실거래): 2,170건 × 0.5초 = ~30시간 ← 동일

리스크:
  • API 과부하 → 응답 지연, 403 오류 가능성
  • 네트워크 오류 → Retry 정책 (3회)가 충분한가?
  • 일정 지연 가능성 → Phase 4 시작 지연

권고:
  • 비동기 병렬 호출 (동시 10개 허용) 고려
  • 토큰 기반 캐싱으로 중복 호출 방지
  • 야간 시간대 API 호출로 서버 부하 분산
```

### 2.3 AI 모델 성능 검증

**문제**: 예상 R² 점수와 실제 성능 괴리
```
현황:
  • 계획서 기준 예상 R²: 0.92 (v1.0), 0.90 (v1.1), 0.93 (vF)
  • PoC 실제 R²: 0.9983 (PoC 청정 데이터 기준)
  • 운영 예상: 0.85 (실제 노이즈 포함)

격차 분석:
  1. PoC vs 운영 환경: R² 0.9983 → 0.85 = 약 0.15 하락
  2. 원인: 실제 데이터 노이즈, 결측치 처리, 이상치 존재

리스크:
  • R² 0.85 미달 가능성 (승인 기준: 90%)
  • 예측가 신뢰도 저하 → 이상치 증가 가능성

권고:
  • R² 목표를 0.85로 조정 (계획서: 0.85 이상)
  • 운영 기준 R² < 0.85 시 대응책 수립 필요
    - 모델 재학습 (추가 데이터)
    - 특성 공학 강화
    - 앙상블 가중치 조정
  • Tier 1 성공 기준: R² 0.80 이상
  • Tier 2 성공 기준: R² 0.85 이상
```

### 2.5 일정 실행 가능성

**문제**: 9일 타임라인이 현실적인가?
```
병목 분석:
  1. Phase 2 (건물 속성): 24시간 실행 (8+16시간)
     └─ 대기 시간 포함 → 실제 3일 소요
  
  2. Phase 3 (가격 정보): 36시간 실행 (12+16+8시간)
     └─ API 호출 대기 → 실제 4일 소요
  
  3. Phase 4 (AI 예측): 16시간 실행
     └─ 병렬 처리 → 실제 2일 소요
  
  4. Phase 5 (검증): 16시간 실행
     └─ 순차 처리 → 실제 2일 소요

총합: 3 + 4 + 2 + 2 = 11일 (계획 9일)

차이: +2일 지연 가능성

권고:
  • 타임라인을 11-12일로 조정
  • 부분 병렬화로 3-4일 단축 가능 (비동기 API)
  • 최종 목표: 10일 (완충 1일)
```
